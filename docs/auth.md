# 로그인·리프레시·로그아웃

## 로그인

`POST /api/auth/login` 요청은 기존 `email`, `password`를 사용합니다. 성공 응답:

```json
{
  "accessToken": "<JWT>",
  "userId": 42,
  "refreshToken": "<opaque-random-token>",
  "expiresIn": 900,
  "refreshExpiresIn": 2592000
}
```

`expiresIn`, `refreshExpiresIn`은 응답 시점의 남은 유효 시간(초)입니다. 기본값은 액세스 15분, 리프레시 로그인 시점부터 30일입니다. `JWT_EXPIRATION_MS`(ms), `JWT_REFRESH_EXPIRATION`(예: `30d`)로 조절합니다. 액세스 기본값은 기존 24시간에서 15분으로 변경했으며 이미 발급된 JWT의 만료 시각은 바뀌지 않습니다.

리프레시는 로그인마다 별도 세션입니다. 서버에는 원본 토큰 대신 SHA-256 해시만 저장하며, 재시작·다중 서버에서도 같은 DB로 상태를 공유합니다. 리프레시는 JWT가 아니며 보호된 API의 Bearer 인증에 사용할 수 없습니다.

## 재발급

`POST /api/auth/refresh`는 액세스 토큰 없이 다음 JSON을 받습니다.

```json
{"refreshToken":"<로그인 또는 직전 재발급에서 받은 값>"}
```

성공하면 로그인과 같은 구조로 새 액세스·리프레시 토큰을 반환합니다. 두 값 모두 교체해야 합니다. 리프레시 절대 만료일은 로그인부터 30일로 유지하며 연장하지 않습니다.

사용한 리프레시를 재사용하면 401을 반환하고 해당 로그인 세션 전체를 폐기합니다. 그 세션의 최신 리프레시도 거부하지만 다른 기기·별도 로그인 세션은 유지합니다. 세션 행 잠금으로 동시 갱신을 직렬화합니다. 중복 요청 중 하나만 성공하고 재사용 감지 후 세션이 폐기되므로, 클라이언트는 동시에 발생한 401을 **하나의 갱신 요청**으로 묶어야 합니다.

회전·재사용 감지는 [RFC 9700 §4.14.2](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14.2)를 참고했습니다.

- 잘못된·만료된·폐기된·재사용 토큰: 401
- 필수 `refreshToken` 누락·공백·과도한 길이: 400
- `/api/**` 응답: `Cache-Control: no-store`

## 로그아웃

`POST /api/auth/logout`에 `{"refreshToken":"..."}`을 보냅니다. 해당 로그인 세션을 폐기하고 204(본문 없음)를 반환합니다. 같은 토큰으로 다시 로그아웃해도 204이며, 알 수 없는 토큰은 401입니다. 이전에 사용한 토큰으로도 그 세션을 로그아웃할 수 있습니다.

이미 발급한 액세스 JWT는 만료까지 유효합니다. 앱은 로그아웃 후 두 토큰과 개인 캐시를 지워야 합니다. 액세스의 즉시 차단·전체 기기 로그아웃 API는 이번 범위에 포함하지 않습니다.

## 프론트 연결

1. 로그인 응답의 두 토큰을 저장합니다. 모바일 리프레시는 OS 보안 저장소에 저장하고 로그·URL에 넣지 않습니다.
2. 보호된 API에는 `Authorization: Bearer {accessToken}`만 전송합니다.
3. 만료로 401이면 재발급을 한 번 수행하고 두 토큰을 교체한 뒤 원래 요청을 한 번 재시도합니다.
4. 재발급도 401이면 토큰을 지우고 로그인 화면으로 이동합니다. 무한 재시도하지 않습니다.
5. 갱신은 병렬로 보내지 않고 진행 중인 하나의 요청 결과를 공유합니다.

이번 변경은 백엔드 인증 API 구현입니다. 프론트 자동 갱신·보안 저장소 연결은 별도 작업입니다. 토큰은 HTTPS로 전송합니다. 웹 클라이언트는 쿠키·CSRF 등을 포함한 저장 전략을 별도로 정해야 합니다.

Flyway V4는 `refresh_session`, `refresh_token` 테이블을 추가합니다. 사용한 토큰 해시는 재사용 감지를 위해 만료까지 유지합니다. 운영에서 만료된 `refresh_session`을 정기 삭제하면 FK의 `ON DELETE CASCADE`로 토큰 이력도 정리됩니다. 검증은 임시 PostgreSQL에서 실행합니다.
